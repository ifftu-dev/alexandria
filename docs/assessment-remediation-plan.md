## Objective and evidence

Repair the authorization, persistence, thread-safety, and lifecycle defects identified in the assessment, then address measured performance and maintainability problems. Preserve the user's authority over changes affecting decentralization, performance, scalability, privacy, and user experience.

The subsequent implementation goal authorizes work on the approved remediation scope. It does not select unresolved recommendations or authorize activation of an unspecified governance protocol. All decisions marked **pending** require an explicit user choice before dependent implementation. Recommendations are proposals, not defaults that become approved through silence. Update this planning artifact as decisions arrive; later changes to normative documentation require the documentation approval prescribed by AGENTS.md.

Rechecked defects include identity-unscoped governance credential queries, insufficient authorization of incoming governance resolutions, non-atomic migrations and vote/tally writes, an unjustified `unsafe impl Sync` on the database wrapper, and startup without rollback. Async lock contention, bundle overhead, and the Sentinel listener ownership problem are risks requiring targeted reproduction or measurement. Large files and concrete dependencies alone are not defects.

The earlier baseline reported 1,178 passing Rust library tests, 13 ignored, 72 passing frontend tests, passing frontend build/typecheck and package Clippy, and a failure of workspace/all-target Clippy in CLI test layout. Those are prior observations, not checks rerun in this new worktree. Dependency advisory results must be refreshed before implementation; cached audit results are not current security guarantees.

## User decision register

### D1 — Governance authority and finality: direction approved

User decision: **DAO committee quorum with independently checked vote evidence; chain anchoring optional.** The operator is not a fallback outcome authority. D4 also requires pending outcomes to wait for quorum to return, and D16 selects a quorum-committed ordered log for inclusion/finality. Epoch transitions, concrete consensus integration, evidence availability, and safe operations still require the design review below.

Current behavior is explicitly the lean model: local SQLite state, signed P2P votes, and operator-signed Cardano anchors. The broader specification calls for decentralized governance. See [protocol §10](protocol-specification.md#10-governance) and [current architecture](architecture.md#9-governance).

Alternatives considered (option 1 selected):

1. **DAO committee quorum plus independently verifiable evidence; anchoring optional. Recommended direction for decentralization.** Removes the platform operator from outcome authority, but adds a protocol for committee epochs, quorum, conflicting certificates, inclusion, and evidence availability. A quorum certificate is not itself proof of every eligible vote's inclusion. This is substantial protocol work.
2. **Harden the existing operator anchoring model first.** Smallest compatibility change, but retains operator availability and trust assumptions. Clearly distinguish provisional local outcomes from anchored outcomes. The anchor commits to data; it does not prove the outcome is correct.
3. **Require on-chain validated finality.** Adds fees, confirmation latency, chain availability, and UTxO contention. Merely requiring a metadata transaction is insufficient: validators must enforce the chosen rules. The deployed reference scripts need a separate suitability review before use.

D1 chooses a direction, not all protocol details. Any staged interim release and its trust claims also need user approval.

### D2 — Performance target approved; budgets/design pending

User decision: **balanced learner devices and larger desktop instructor workloads**. Evaluate learner responsiveness and memory alongside larger instructor catalogs and sustained background sync. Neither the smallest phone nor a dedicated high-volume operator node alone determines the architecture.

Executor queue decision: **reserve 16 learner, 8 instructor, and 8 background waiting slots; dispatch continuously backlogged lanes with exact 8:4:1 weighted fairness; reject overflow immediately as retryable busy work.** One lane cannot consume another lane's reservation. This bounds queued memory and preserves interactive admission while guaranteeing background progress. It does not approve a read pool, define automatic retries, or settle the remaining device-level performance budgets.

After that choice, present measured baseline results and concrete proposed budgets for p95 interactive latency, unlock/lock latency, peak memory, background CPU, disk use, and sync backlog recovery. Do not invent accepted SLA numbers. Include supported OS versions, representative physical devices, dataset sizes, peer counts, and network conditions in the benchmark contract.

Database options to compare are a bounded worker owning one connection, bounded blocking tasks around the current serialized connection, and one writer plus a small bounded read pool. The latter may improve read throughput while increasing memory, encryption-key lifetime, teardown complexity, and checkpoint pressure. Select the design after measurement and user approval. `RwLock<Connection>` is not a valid concurrency shortcut.

Candidate benchmark contract for approval after baseline collection:

| Scenario | Proposed fixture | Proposed acceptance budget, not yet approved |
| --- | --- | --- |
| Learner dashboard during sync | Representative 4–6 GB mobile device; 10,000 catalog rows, 25,000 credentials; 8 simulated peers | p95 local interactive reads at most 250 ms; dashboard usable within 1 s after its data request |
| Larger instructor workspace | Representative 16 GB desktop; 100,000 catalog rows, 250,000 credentials, 500,000 signed votes; 64 simulated peers | p95 local interactive reads at most 500 ms during background ingest |

Fixture rows must form valid relationships and exercise realistic queries/payload sizes. Dataset numbers, hardware examples, and budgets above are proposals to make measurement reviewable, not claims about current performance. Record idle/peak RSS and battery/CPU as well; propose absolute memory and unlock-time budgets from measured platform baselines without weakening password derivation or encryption.

### D3 — Locking and profile-switch experience: approved

User decision: **hide private content immediately, show `Locking…`, and enable the next unlock only after cleanup succeeds**. Implement backend operation admission closure with this UI state; keep progress/recovery visible if teardown fails. Do not overlap profile startup with old-profile cleanup.

Alternatives considered: immediately hide private content and show `Locking…` until cleanup succeeds (selected); hide immediately and overlap cleanup with the next profile's startup; or retain the current view under a blocking progress overlay until cleanup finishes.

### D4 — Submission, approval, election, and committee-time policies approved; protocol details pending

User decision: **keep outcomes pending when committee quorum is unavailable and resume when quorum returns; no operator override.** Elapsed time must not lower the quorum requirement, finalize an outcome automatically, or activate another authority. A permanent quorum loss can therefore leave outcomes pending indefinitely; electorate-controlled recovery is not selected. Persist pending state across restarts and show the reason for waiting. Resume only after the required evidence and valid quorum are available. Waiting for finalization does not extend voting deadlines.

User decision: **require a verifiable committee receipt before the cutoff; show `Submitted` only after receipt.** A locally saved or signed vote is a draft/queued vote until it has the required receipt. No submission grace period is selected. Votes without proof of timely certified submission do not count; timely certified votes delivered later to another verifier retain their submission evidence and must be handled under the inclusion protocol. Do not relabel an unreceipted queued vote as submitted after the deadline. The quorum and certified-time rule is fixed below; omission handling and data availability remain in the protocol review. One committee signature or an uncorroborated timestamp is never sufficient.

User decision: **enforce the cutoff using receipt times independently signed by five of the seven committee members, followed by a five-of-seven close certificate; require neither Cardano nor a centralized timestamp service.** Each receipt signer signs the exact vote/log/evidence/rules/epoch binding together with its own observed receipt time. Only valid distinct-member attestations at or before the fixed cutoff can form the submission quorum. The deterministic certified time is the fifth-earliest valid member time; it is descriptive metadata, while validity comes from five independently asserted pre-cutoff observations. The close certificate binds the same DAO, epoch, rules, cutoff, closed log root and length, vote-set commitment, and deterministic result commitment; five valid distinct members must sign it at or after the cutoff. This trust model assumes no more than two committee members violate the protocol and still requires explicit member clock-operation rules and monitoring; signatures prove what members attested, not an external physical-time fact.

User decision: **each committee node must use independently sourced authenticated time, refuse governance signatures when its estimated clock error exceeds 30 seconds, apply the exact cutoff without a grace period, and warn that submissions in the final 30 seconds may fail to assemble quorum.** The operational error bound is per signer; it does not shift the proposal cutoff or let a verifier accept a late attestation. Receipt attestations must commit to reviewable clock-health metadata so peers can enforce the declared bound, while the exact authenticated source/proof format and source-diversity monitoring remain part of the wire/operations review. A dishonest signer can still misstate its clock condition, which is why one signature remains insufficient and the approved Byzantine threshold still applies.

User decision: **evaluate credential eligibility at certified vote submission and preserve evidence of that decision for later verification.** Bind the vote/receipt to the applicable eligibility rules, credential/status evidence, identity binding, and committee epoch. Finalization verifies that historical submission evidence rather than silently reevaluating qualification against the verifier's current credential state. Treatment of subsequently discovered fraud or evidence that the credential was already invalid at submission remains an explicit protocol decision; this choice does not make invalid evidence valid.

User decision: **keep two-thirds proposal approval and require a DAO-configured minimum turnout declared before voting opens.** Bind the turnout requirement to the proposal's certified opening rules; do not change it during voting or confuse the five committee signatures with voter participation. Use exact integer arithmetic at the boundary.

User decision: **express minimum turnout as a count of distinct eligible voters, fixed before voting opens.** Do not estimate a percentage from peer-local credential inventories or require an electorate-size snapshot. Multiple devices, signatures, or qualifying credentials belonging to one voter cannot inflate turnout; bind counting to the reviewed voter identity/uniqueness rules. Eligibility still follows the certified-submission policy, and only valid, timely certified votes can count. Treatment of abstentions and valid configuration ranges remain part of the concrete rule specification.

User decision: **run a runoff among candidates tied across the final available committee seat; keep the existing committee until the replacement is certified.** Local ordering, node arrival time, operator choice, and random selection must not break the tie. A tie wholly inside or outside the elected set does not by itself require a seat-boundary runoff. Define runoff opening/cutoff and eligible participation in the reviewed election rules; the tie does not automatically install a partial replacement committee or reduce its threshold.

User decision: **keep a submission pending verification and fetch missing required credential evidence from peers with bounded retries; no receipt until verified.** Missing evidence is not proof of ineligibility. Bound request size, concurrency, per-peer work, attempts, and backoff; persist the pending reason and retrieval progress. Exhausted retries must not count the vote, issue a receipt, or manufacture an ineligibility finding. A retry or late evidence arrival never extends the cutoff: without a valid five-signature receipt certified before that cutoff, the vote is not submitted and cannot count. The UI distinguishes pending verification/retry exhaustion from certified submission. Evidence already certified in a timely receipt may be retrieved later by another verifier without invalidating that original timeliness proof.

Approve a concrete protocol proposal covering:

- Complete the committee receipt/close wire integration and offline verification path implementing the approved five-of-seven timing policy. A voter timestamp or one committee timestamp is not independent proof of timely submission. Do not add mandatory chain timestamping under D1's optional anchoring choice.
- How historical credential/status evidence and signing-key rotations are verified at certified submission, and how a later fraud finding is handled. Implement the approved eligibility time without introducing an election-opening snapshot or finalization-time qualification gate.
- Concrete retrieval bounds, retry/recovery controls, and cutoff transitions implementing the approved pending-verification policy. Unverified votes cannot enter an authoritative tally or receive a submission receipt.
- Inclusion acknowledgements, omission detection/challenges, safe partition recovery, vote equivocation, abstention/no-vote behavior, distinct-voter counting and valid turnout configuration ranges, and runoff scheduling under the approved policies. Proposal approval threshold, receipt signer threshold, and outcome certificate quorum are separate parameters.
- The exact vote-specific public evidence bundle and consent presentation implementing approved D10. Exclude unrelated history; do not change the separate nomination disclosure rules without reconciling the specification.

Present the resulting state machine and wire schema for review before coding the protocol. Safety, availability during partitions, and immediate finality cannot all be promised without explicit assumptions.

### D8 — Public founding roster: approved; roster contents and activation details pending

User decision: **use a public, one-time founding roster for each DAO, explicitly accepted as its initial trust anchor; subsequent committees are elected.** This approves the bootstrap method, not a specific set of people, keys, or an automatic appointment by the platform operator. Real roster contents, evidence of independence/qualifications, acceptance mechanism, and activation epoch must be made reviewable before activation.

The current `commands/governance.rs::create_dao` installs the operator as sole initial committee and defaults committee size to one. That bootstrap cannot be carried into D1's new model without an explicit trust decision.

Alternatives considered (option 1 selected):

1. **A public, one-time founding roster per DAO, explicitly accepted as its initial trust anchor; subsequent committees elected. Recommended.** This is a disclosed founding trust assumption, not an evidence-derived election. Record the real independent participants, acceptance signatures, scope, initial keys, governance rules, protocol version, and genesis hash. Their qualifications and how the community accepts the roster need review. No software-update key may silently replace an established DAO's genesis or committee.
2. **An initial election among credential-qualified participants.** Requires a defined initial electorate, credential trust/identity rules, and a separate method of certifying the bootstrap election before there is a committee. A self-signed roster or an unbounded collection of public keys does not solve that circular trust problem. Activation waits for the reviewed bootstrap process.

Bind the DAO identity to its accepted genesis and prevent peers from accepting another genesis under the same identity. DAO scope labels alone are not unique authority identifiers. New-DAO creation, parent/sub-DAO recognition, and later elected committee transitions must follow the reviewed recognition rules; do not infer that a platform maintainer may appoint future committees. Acceptance tests must reject substituted genesis/rosters, a software-update attempt to reset an established trust anchor, and an unelected replacement committee lacking the required transition proof.

### D9 — Seven-member, five-signature launch committees: approved

User decision: **seven independently controlled committee members, requiring five signatures for submission receipts and final outcomes; quorum remains reachable with up to two unavailable members.** Extra keys/devices controlled by one member never count as additional members. A DAO that cannot establish seven independent members does not activate by reducing the threshold. The actual founding roster remains subject to D8's explicit acceptance.

The approved launch threshold is `n=7, q=5`, with equal certificate weight per independently controlled member. The general formula `q = floor(2n / 3) + 1` is a proposal for any future approved resizing, not authority to resize automatically. This threshold certifies valid protocol actions; expertise-based election/membership and the approval ratio of a proposal remain separate rules.

| Option | Required receipt/finality signatures | Unavailable members while quorum remains reachable | Proposed Byzantine fault assumption |
| --- | --- | --- | --- |
| 7 independent members (selected) | 5 | At most 2 | At most 2 Byzantine members, with the complete reviewed consensus protocol |
| 4 independent members (not selected) | 3 | At most 1 | At most 1 Byzantine member, with the complete reviewed consensus protocol |

The fault bound counts faulty and unavailable participation together for progress; it is not an allowance for both maximum Byzantine faults and additional outages. If fewer than the selected minimum independent members are available to establish a DAO, it remains inactive rather than manufacturing extra keys or reducing quorum. More members increase recruitment/operations and message costs. Changing committee size/weight later requires an authorized protocol transition; a node cannot edit a local setting to change the threshold.

For `n=7`, any two size-5 signer sets intersect in at least 3 members. Under at most 2 Byzantine members, at least one intersecting member is honest. This simple set argument motivates the threshold, but safety also requires durable anti-equivocation and round/locking rules; it is not a proof of a new consensus implementation. The [CometBFT consensus specification](https://github.com/cometbft/cometbft/blob/v0.38.0/spec/consensus/consensus.md) documents a complete voting/locking protocol using more than two-thirds. [HotStuff](https://arxiv.org/abs/1803.05069) is another published protocol under partial synchrony. These are design references, not selected dependencies or a decision to run a new public blockchain.

### D10 — Consented vote-specific public evidence: approved

User decision: **publish only the specific signed credential/status evidence required for the vote, with explicit consent; no unrelated history.** Peers must be able to verify the underlying eligibility evidence independently. Committee-private evidence with certificate-only trust is not selected. Bind the consent to the exact disclosure and vote context; do not reuse a generic profile opt-in as authorization to publish additional credentials.

Public evidence means the actual signed fields required by the credential scheme may reveal identity, qualifications, or other included claims. Show exactly what will be disclosed before consent; do not suggest that a signed JSON credential can be arbitrarily redacted and still verified. Publish no unrelated history. A voter declining disclosure must retain access to learning and private credentials, but cannot obtain a receipt under a public-proof policy without its required evidence. Network copies of published evidence cannot be recalled by deleting a local record; consent must explain that consequence.

Acceptance: without consent, publish neither the vote's credential evidence nor the vote for certification. The consent preview matches the actual disclosed bundle. Unrelated credentials and history never enter the bundle. Another peer can verify the vote's qualification from the approved published evidence, identity binding, rule version, and certified submission context. If a credential format necessarily discloses additional signed fields, show them and allow the learner to decline rather than silently redact or publish them.

### D11 — Member-operated committee nodes: approved

User decision: **each committee member operates a node and controls its governance signing key; ordinary learners remain clients.** Delegated signing custody is not selected. Define a committee-node runtime that can stay available independently of a learner's foreground Tauri session, with local protected keys, durable consensus signing state, bounded evidence storage, and catch-up after restart. No launch operator holds a quorum of member signing keys.

Distinguish the committee governance signing identity from general wallet capabilities in the reviewed key-binding design. Member-controlled hosting may use independently managed infrastructure, but multiple processes on one account or extra devices do not create independent committee members. Record shared failure domains when evaluating availability; do not advertise two-fault tolerance without the selected independence assumptions. Do not provision infrastructure, acquire hosting, or assign actual hosts/keys during planning.

Acceptance: five of seven independent member nodes can issue valid receipts/outcomes under the reviewed protocol; four cannot. Restart cannot erase anti-equivocation state or cause double signing. A learner client need not run a committee service to submit or verify a vote. Stopping the learner UI does not silently stop a separately running committee service, and the service cannot sign under another member's identity. Deployment tests use local controlled nodes; public operation waits for actual member setup and genesis acceptance.

### D12 — DAO-approved qualification policy: approved; policy contents pending

Bind the policy identifier/version and its contents to the certified opening rules, and bind each submission's eligibility evidence to that policy. Do not change accepted issuers or assessment requirements retrospectively within an open vote.

The founding roster's explicit acceptance must also make the initial qualification policy reviewable; later policy updates require an authorized governance transition. In particular, the current `course_authority_key(author_address)` is deterministically derived from public input; do not automatically install those keys as trusted governance issuers merely because a credential signature verifies. Unknown or disallowed issuers cannot qualify a voter merely by issuing a high-level claim; missing required verification material follows D4's bounded pending retrieval. Later verifier policy changes do not silently rewrite eligibility certified under a historical policy. No global operator-controlled issuer allowlist is introduced by this choice.

### D13 — Uncertain chain submissions during locking: approved

User decision: **durably preserve the exact signed transaction as “outcome unknown,” finish local cleanup once the bounded operation has stopped, and reconcile that same transaction on the next unlock without automatically creating a replacement.** Persist signed bytes, the locally computed transaction identity, and the operation's recovery context before network submission. A timeout, cancelled request, lost response, or a later “not found” response does not establish rejection. Do not release the profile lease while the old operation still owns profile resources.

Recovery must work after interruption between sending and updating the domain row, and must not require the original signing key just to query the original transaction. An acknowledged submission is not a confirmed chain outcome. Prevent duplicate invocations from bypassing the durable binding by allocating a new operation identifier. Keep this journal local to the encrypted profile database; do not gossip signed transactions or recovery context. This does not change D1/D4 committee finality or make chain anchoring mandatory.

Acceptance: cancel or time out after the signed request leaves the client; complete resource cleanup, reopen the same profile, query the original transaction, and restore its domain status without another POST or replacement build. Missing/unavailable chain evidence leaves the operation uncertain. A failed journal commit must prevent sending. Confirmation and dependent local pointers must recover atomically. **The user also approved 10-second connection and 30-second total request limits.** Enable those production limits once all submission callers preserve uncertain outcomes; the initial journal/queue integration does not yet enable them globally.

### D14 — Genuine completion endorsement and offline issuance: approved

It could not prove instructor control or independent endorsement; the identity resolver also labelled these derived DIDs as instructors. D12 excludes treating those signatures as trusted governance qualifications. The decisions below govern the replacement; implemented changes and remaining gaps are recorded in the progress section.

User decision: **issue learner self-claims immediately offline; add genuine instructor endorsement separately only when the instructor signs.** Completing a course must not require instructor availability, and the local device must not manufacture an independent issuer or instructor signature. Remove the artificial independent-issuer confidence boost. Review existing affected credentials, issuer labels, confidence calculations, and real attestation acquisition before the rollout; D5's governance cleanup does not itself authorize deleting unrelated completion credentials.

Historical exclusion decision: **exclude only issuers proven to use the public-derived key.** Match the signed issuer DID to the legacy derivation from an available public author address; an assessment-method label, credential type, or missing metadata alone does not establish that match. Preserve the original credentials. Do not quarantine ambiguous historical attestations or reduce their scores merely because their origin cannot be classified. Retain recognition evidence and invalidate/recompute affected derived scores without deleting unrelated credentials or history. The user declined the broader ambiguous-legacy quarantine proposal.

Background witness decision: **persist optional completion witnesses in the existing profile-scoped background worker and resume after restart.** Local self-claims return without provider I/O; the UI shows the witness as pending until confirmed and never creates a replacement for an already signed transaction. Preserve profile ownership and the original evidence across retries. This does not change the treasury/learner funding policy or authorize a separate background service while the profile is locked.

That label is not a safe exclusion predicate. Known author addresses can establish exact matches, including when the credential predates this change. Enforce the exclusion in both aggregation and reputation sampling, and cover cached/direct readers (`commands/aggregation`, `commands/reputation`, `commands/evidence`, `commands/talent_index`, and reputation snapshot construction). Recognition must survive course removal or author changes, and newly discovered matches must invalidate affected current caches. Historical derived-state snapshots need explicit treatment so an old inflated value is not presented as a current valid score. None of this authorizes removing original credentials or silently classifying unmatched issuers as compromised.

### D15 — Reputation snapshot semantics and credential-hash anchoring: approved

The snapshot command labelled all-time reputation scores with a rolling 30-day window, queried DID-backed reputation using a stake address, and regenerated its inputs at submission. The checked-in `cardano/governance/validators/reputation_minting.ak` additionally requires a designated `authorized_minter`, whereas `commands/snapshot.rs` signs with the learner wallet only. This source review is not independent verification of the deployed script's parameters or suitability. The current codec also emits computation-spec integer 2 while the rebuilt reputation engine identifies its calculation as `v3-vc`; the replacement must declare the actual calculation and confidence semantics rather than carry forward a misleading version label.

User decision: use an explicit **as-of snapshot of all eligible evidence**, not a rolling 30-day score. The implementation declares this scope consistently in frozen inputs and persisted metadata; existing signed transactions retain their original bytes and interpretation rather than being rewritten or replaced. The downstream user-facing snapshot view remains to be updated when it is implemented.

Anchoring decision: use the **existing credential-hash anchor path** for optional reputation snapshots, not CIP-68 reputation tokens or a new committee-authorized minter. Implemented snapshots bind the anchor to a signed DerivedCredential containing the preserved as-of evidence/score inputs and remain locally available without a chain request. Existing signed CIP-68 transactions remain original recovery-only records and are never relabelled, rebuilt, or replaced.

D1/D8 transition decision: retain the legacy operator-only `create_dao` command **only in explicitly enabled development builds**. Both conditions are required: a development build and an opt-in build feature. This dual compile-time gate is implemented and was checked in both debug and release configurations. Release builds do not gain this authority through diagnostics mode or an incidental runtime setting. The current one-operator bootstrap is not the implementation of the approved seven-member founding roster.

Taxonomy transition decision: **taxonomy changes do not auto-create active DAOs before the seven-member founding roster is explicitly accepted. Keep the caller-supplied legacy taxonomy-ratification command only in an explicitly enabled development build.** The same fail-closed boundary applies to legacy taxonomy gossip, which carries only one transport signature and a caller-declared ratifier list; leaving that path active would bypass the approved five-of-seven evidence rule.

### D16 — Quorum-committed ordered governance log: approved

User decision: **use a five-of-seven Byzantine-fault-tolerant replicated ordered log. Committee members lock one quorum-certified prefix per position; submission receipts are issued only after the containing vote is committed; closing certificates must extend that committed prefix.** This replaces peer-arrival ordering and operator-selected subsets as the finality basis. A locally saved, gossiped, or merely acknowledged vote remains unsubmitted until the log commitment and receipt quorum exist.

The implementation must persist consensus votes/locks before signing, preserve them across restart and round/leader changes, reject conflicting prefixes, and provide catch-up plus inclusion evidence. A close certificate must be verifiably linked to every counted receipt's committed prefix; comparing two unstructured root strings is insufficient. Five signatures collected in one round without a safe round-change protocol are not an implementation of this decision. Cardano remains an optional anchor of the resulting certificate, not a participant in consensus.

This decision approves the safety/finality architecture and its extra consensus traffic per round. D17 selects the consensus core and process boundary. Retention limits and the deployment resource envelope still require evidence and review because those choices materially affect committee-node performance and operability.

### D17 — CometBFT committee-node integration boundary: approved

User decision: **use CometBFT v0.40 as a separately packaged committee-node consensus process, with an Alexandria Rust ABCI application, equal voting power for each of the seven independently controlled committee members, and receipt/close evidence derived from committed block inclusion plus the signed commit vote timestamps.** This adopts a mature Byzantine consensus core instead of implementing new locking and round-change logic inside the learner application. It does not turn governance into a public cryptocurrency chain and does not make Cardano anchoring mandatory.

The Rust application remains responsible for deterministic governance validation and state transitions: founding-genesis/epoch authority, frozen proposal rules, credential-policy and evidence checks, vote uniqueness, cutoff handling, committed-prefix/result commitments, evidence retention, and epoch handoff. CometBFT is responsible for ordering, consensus rounds, validator-set agreement, durable consensus state, and catch-up. ABCI proposal preparation/process/finalization must be deterministic; external evidence fetch and provider I/O cannot occur inside consensus execution. A vote lacking locally available admissible evidence remains outside the proposed block until pre-consensus verification succeeds.

Receipt and close proof formats must bind the Alexandria event bytes and application hash to a concrete CometBFT height/block/commit. Verification must check at least five distinct equal-power members from the active seven-member epoch and apply the approved clock-error/cutoff rules to their signed commit vote timestamps. Do not expose CometBFT's RPC or private-validator signer broadly to learner clients; committee endpoints need authenticated submission, bounded requests, rate limits, and proof-serving APIs. Each committee member retains independent custody of its consensus and governance keys.

This selects the component boundary, not deployment topology, hardware sizing, retention/pruning limits, snapshot cadence, endpoint-discovery policy, or upgrade procedure. Package/version pinning, reproducible binaries, advisory review, ABCI compatibility tests, crash/catch-up tests, four-node partition safety, and three-node-loss liveness recovery are required before activation. The legacy governance path remains fail-closed in release builds throughout the transition.

### D18 — Genesis-derived DAO identity and explicit trust-anchor pinning: approved

User decision: **derive each DAO ID from its canonical genesis core, recognize that ID only after every founding member's acceptance of the core has been verified, and require clients to explicitly import and pin that genesis before trusting the DAO.**

Subsequently approved amendment (2026-09-15): the original decision derived the ID from the fully signed envelope. Ed25519 signatures over identical content can differ, so one founder re-signing an unchanged core produced a second, twin DAO ID with the same name, scope, keys, and rules, and a preview could not tell the two apart. The user approved deriving the ID from the core alone, which closes that twin-DAO issue. All seven acceptances and all 21 key-control proofs are still required before the ID identifies a DAO. Discovery, a human-readable scope/name, a platform default, or a software update cannot silently select a canonical DAO or replace an established trust anchor. Competing genesis documents create distinct DAO identities; choosing which one to trust remains an explicit client/community decision.

The genesis format must avoid circular self-reference. Define canonical, domain-separated genesis-core bytes without a DAO ID; bind the scope, protocol and rule versions, seven founding member identities and consensus/governance keys, five-signature operational thresholds, initial qualification policy, and activation parameters. Every listed founding member must sign that same core as its one-time roster acceptance. Canonically order and verify the complete signed envelope. The DAO ID is the domain-separated hash of the core and is valid only once that verification succeeds. A five-member operational quorum cannot manufacture an omitted founding member's acceptance or activate a nominal seven-member roster that was never fully accepted.

Import must show the derived ID/hash and material trust facts before pinning, verify every founding signature and independence constraints that can be checked mechanically, and persist the exact genesis bytes as the local trust anchor. Sync, discovery, Cardano anchors, and later committee certificates may locate or corroborate bytes but cannot auto-pin, overwrite, or reset the trusted genesis. Removing a local pin is a deliberate local trust-management action, not a governance outcome; importing a competing genesis creates trust in a different DAO ID rather than a fork under the old identity.

Acceptance tests must reject non-canonical encodings, reordered/duplicate/missing members or signatures, altered rules/policy/keys, a claimed ID that does not match the fully accepted core, a re-signed envelope that attempts to mint a second ID, substitution under an existing human-readable DAO name, and update/sync attempts to replace a pinned genesis. Identity, canonicalization, the portable locator/import boundary, and bounded retrieval scheduling are settled below; locator publishing/export remains subject to its performance and user-experience review gates.

Transport decision: **canonical JSON is the authoritative founding-genesis artifact. QR codes and deep links carry only the genesis-derived DAO ID plus multiple content-addressed retrieval locations; they never contain enough authority to auto-pin.** Opening a locator may normalize and display its identifiers without network access. Retrieval is a separate action, must reproduce the declared BLAKE3 hash and the DAO ID derived from the core of the fully verified canonical envelope, and must then show the complete material trust preview. Pinning remains a third explicit action requiring confirmation of the full DAO ID. A full embedded-genesis QR is not part of the protocol.

Retrieval scheduling decision: **race at most three locator sources concurrently, with a ten-second limit for each source and a 30-second limit for the complete retrieval.** The first result that passes both content-hash and full genesis verification wins; completion or timeout cancels the remaining attempts. Source order is discovery preference only and conveys no authority. Exhaustion or timeout leaves trust state unchanged and does not pin partial or unverified bytes.

## Concrete protocol proposal for the next design review

This section translates the approved D8/D9/D16/D17/D18 direction into checkable invariants. Authenticated-time proof details, source-diversity monitoring, concrete evidence retention, packaging, and remaining privacy details remain review gates; the genesis-derived identity, ordered-log architecture, CometBFT/ABCI boundary, and per-signer 30-second clock-error limit are approved.

### Agree on an ordered record before issuing a receipt

Approved direction: an authenticated, durable governance event log per DAO/epoch, whose committed entries are certified by five of seven independently controlled committee members using a reviewed Byzantine consensus protocol. A submission receipt proves the vote is already included in a committed log entry, rather than promising to remember a vote for a later unrelated tally. A finalized outcome names a certified closed prefix and is derived from its valid votes. Peers retrieve the same committed evidence, not whichever gossip happened to reach their local database first.

The log must provide safe leader/round changes, persisted signing decisions, catch-up, and authorized epoch handoff. Do not implement a one-round `collect q signatures` shortcut or sign whichever conflicting result arrives first. Prefer an existing verifiable protocol/core if it fits the Rust/mobile/deployment constraints; present integration and resource costs before selecting it. An ordered log does not itself require a publicly mined chain, global token, or mandatory Cardano write.

Proposal lifecycle sketch: approved publication rules → voting open → committed eligible submissions → certified close → deterministic outcome certificate. These are domain phases, not a substitute for the underlying agreement protocol. After the deadline, no new uncertified submission can become a timely vote. When quorum is unavailable, the close/outcome remains pending; restart preserves that state and does not change the deadline.

Certifying a closed prefix prevents silently omitting its included votes, but does not prevent committee members from censoring a request before it earns a receipt. The client must therefore keep an unreceipted request visibly queued/unsuccessful, and attempt multiple committee endpoints with bounded retry. Do not claim guaranteed inclusion during an outage or Byzantine majority.

### Evidence contracts to review before wire changes

| Artifact | Required bindings and checks |
| --- | --- |
| Genesis/epoch | DAO identity and scope, protocol/rule versions, independent member identities and keys, thresholds, authenticated activation/transition proof |
| Signed vote | DAO and election/proposal identity, voter identity, choice, replay/equivocation identifier, exact canonical signed bytes, qualification evidence reference |
| Submission receipt | Vote hash, log position and inclusion proof, certified submission time, applicable rule/evidence versions, epoch, unique committee signers and protocol commit proof |
| Closed vote set | Certified log prefix/root, applicable cutoff, vote count, evidence availability references; no arbitrary sender-provided subset |
| Outcome certificate | Closed-set reference, deterministic totals/winners, rule version, decision status, epoch and required commit proof |
| Committee transition | Elected membership, prior epoch authority, last certified boundary and new epoch keys; no acceptance under an unrelated/new self-proclaimed committee |

Use canonical domain-separated signing and checked integer arithmetic. Reject unknown incompatible versions, wrong DAO/epoch, duplicate signers, malformed keys, invalid counts and proof references. Persist enough evidence to verify all new-protocol history after key rotation; a later revocation does not silently redefine qualification time, but proven prior invalidity/fraud needs the still-pending adjudication rule.

The wall clock on the voter's device is advisory. The approved certificate rule uses the fifth-earliest independently signed valid committee receipt time and admits only signatures whose asserted time is at or before the fixed cutoff. The close certificate admits only signatures at or after that cutoff. This removes reliance on one caller-provided timestamp, Cardano, or a centralized time service, but does not independently prove physical time. Committee-node clock-operation/skew monitoring and boundary tests still need concrete numerical bounds; no uncertainty window may silently become a submission grace period.

### Data availability, privacy, and deployment costs

The existing gossip message limit is 64 KiB. Announce small certificates/references; fetch large evidence sets through bounded, content-addressed retrieval. Count signatures, proof depth, bytes, concurrent fetches, and per-peer pending requests before allocation. Signers must hold the data whose availability they attest to under the selected retention policy. Learners must be able to retain their receipts and retrieve evidence from multiple peers, without requiring the platform operator or one storage provider.

Implement D10 by publishing the exact consented, vote-specific signed credential/status evidence for independent peer verification. Do not substitute committee-private checks, add unrelated history, or invent selective-disclosure cryptography that the credential format does not support. The remaining design work is the concrete evidence schema, availability/retention, and consent preview, not reselecting the public/private policy.

Implement D11 as member-operated committee services, separately from ordinary learner clients and their foreground profile lifecycle. Benchmark service resource use, per-DAO overhead, evidence retention, bandwidth, and restart/catch-up alongside D2's learner/instructor workloads. Runtime packaging and actual infrastructure remain implementation/deployment proposals; do not centralize signing custody or make ordinary learner phones run always-on validators. No server provisioning or new infrastructure subscription is authorized by this plan.

`sentinel_priors.proposal_id` references governance proposals, and opinion withdrawals reference DAOs. Therefore a broad `DELETE FROM governance_proposals` or `governance_daos` is not a complete cleanup plan. Preserve underlying user content and credentials; separate data possession from its old ratified/trusted label. Present any user-visible effect on previously ratified content or Sentinel models before changing that behavior. Test the approved dependency cleanup with foreign keys enabled and ensure built-in trusted fixtures have an explicit new-protocol basis.

- Separate ordinary interruption recovery from pre-existing corruption. Detect and explain damaged histories; recovery must preserve the original database and obtain approval before repair or restoration.

Acceptance: failure injected between every relevant write rolls back the entire operation; restart/retry applies exactly one logical vote or migration; duplicated delivery does not increment twice. Test file-backed SQLCipher upgrade/reopen as well as in-memory migration fixtures. Outbox tests cover crash before/after send and prove bounded retry behavior. Cleanup fixtures verify removal of targeted legacy governance state, foreign-key integrity, preservation of unrelated records, safe restart, and no reappearance after seed/sync/outbox replay.

Dependencies: W2 for safe ownership. New-event atomicity can proceed independently; historic remediation and protocol outbox replay require D5/W5.

### W4 — Centralize governance invariants

Scope: a focused governance domain service, `commands/governance.rs`, `p2p/governance.rs`, `domain/governance.rs`, and credential/registry verification boundaries.

- Define an authenticated actor derived from the verified signing key and registry binding; map that identity to credential `subject_did`. Do not trust a request-supplied DID or select any qualifying credential in the database.
- Write an action-by-action rule matrix for proposer, reviewer, voter, nominee, phase transition, resolution, and committee installation. Include local commands that currently lack wallet/actor checks. Preserve documented scope-specific exceptions such as Sentinel open proposals explicitly.
- Use the same pure eligibility and transition rules from local IPC and incoming events. Pass certified submission time and the corresponding verified historical evidence through narrow interfaces. Distinguish live submission validation from later verification of an already certified submission. Keep storage and networking outside the rule evaluation.
- Validate entity-to-DAO binding, actor binding, legal state transitions, values/counts, and newly supplied deadlines/thresholds. Missing data, invalid data, and a database failure must have distinct outcomes. Prevent publication from bypassing required committee review.
- Perform state-dependent checks and writes against one consistent transaction view; prior signature/credential verification must be bound to the evidence/version actually used.

Acceptance: an unrelated user's credential never grants eligibility; spoofed proposer and cross-DAO messages fail; published proposals cannot bypass review; local and remote forms of the same authorized action produce equivalent state. Cover the documented Sentinel exception separately. Historical eligibility and finality tests follow the explicitly approved D1/D4 rules.

Dependencies: W1–W3. Actor binding and unambiguous existing rules can be fixed first; finality, bounded evidence retrieval, and legacy cutover must implement D1/D4/D5 and the remaining protocol review.

### W5 — Make replicated outcomes independently checkable

Scope: governance event schemas/handlers, P2P retrieval/sync, vote storage, governance UI status, and Cardano outcome anchoring.

- Specify and implement D1/D4: committee/authority epochs, exact certificate quorum where relevant, vote-set commitment and availability, cutoff evidence, deterministic tally/winner rules, equivocation handling, and finality transitions. Any eligible verifier can check the outcome without trusting a relay or a platform API response alone.
- Persist or reference the original signed envelope and the verification evidence needed to replay every new-protocol vote. Existing vote tables store signature/public key, while the signature covers additional envelope fields; a hash or signature column alone is insufficient. Remove unverifiable pre-launch records under D5 rather than attempting to certify or recover them.
- Separate live-message freshness checks from historical verification of new-protocol evidence. Replay must verify the original signature and the approved eligibility/time rules; do not discard a valid certified vote merely because it is old, accept unsigned rewrapped payloads, or reintroduce discarded pre-launch records.
- Bind a committee receipt to the exact vote and its certified eligibility evidence; only expose `Submitted` after a verifiable pre-cutoff receipt is available. Persist queued, submitted, and failed/expired submission state across reconnect/restart. Do not confuse a submitted vote with a finalized outcome. Verify timely certified votes received after cutoff through the historical-evidence path, with omission/inclusion rules approved before implementation.
- Replace blind acceptance of `ProposalResolved`, transmitted winner lists, and committee changes with approved proof requirements. Recomputing a locally incomplete tally alone is insufficient for finality.
- Make `pending evidence`, `provisional`, `final`, and `conflicting` states explicit according to the approved UX/protocol; no successful-looking status for unverifiable input. Retry missing evidence through bounded peer requests and durable state.
- Preserve a pending outcome throughout quorum outages, including across app restarts. Do not add an operator override, reduced quorum, timeout finalization, or an unapproved recovery authority. Resume normal verification/finalization when quorum returns without extending the approved submission cutoff.
- Version incompatible wire changes and implement D5's fresh governance cutover, cleanup, and legacy-event rejection. Obtain the user's decision on initial committee/epoch bootstrap before activating authority. Do not introduce a new centralized authority or alter gossip topics incidentally. Check anchors against the same certified outcome and evidence set; a Merkle root is a commitment, not a validity/completeness proof.

Acceptance: multi-node tests cover shuffled/duplicated/delayed delivery, partitions/rejoin, missing credentials, authority rotation, conflicting finalizations, replay, and forged resolution. Nodes with the same certified evidence agree; nodes without it remain explicitly non-final. Advance time and restart nodes during a quorum outage: outcomes remain pending without falling back to another authority, then resume safely when quorum returns. Test unavailable operator/relay/chain behavior against D1. If on-chain enforcement is selected, add validator and preprod integration verification before release.

Submission-specific acceptance: a queued offline vote never displays `Submitted` without a valid receipt; an unreceipted vote after cutoff is not counted; forged/backdated receipts fail; a valid pre-cutoff receipt remains verifiable after delayed delivery and restart. Eligibility tests use the certified submission evidence, including historical identity/key binding, rather than silently applying later qualification changes. Boundary tests use an injected protocol clock and the approved receipt-time rules.

Dependencies: approved D1/D5/D8/D9 policies, actual genesis/activation details and remaining D4 decisions, and W3/W4. This is the largest decision-dependent work package; estimate it after the concrete protocol design, not as a small refactor.

- Give Sentinel one owner for listener registrations, timers, async startup, and cleanup. Use a generation/token to prevent a late startup callback from reactivating a stopped session. Consumers of reactive debug state must not acquire independent cleanup ownership.

Acceptance: inject failures at each mandatory startup stage; all initialized resources are reclaimed, keys cleared, and retries succeed. Test concurrent start/stop/switch, a task completing after lock, shutdown failure, and profile A/B isolation. Repeated Sentinel mounts/starts/stops leave zero stale listeners/timers and one session at most. Confirm D3 manually on a supported desktop and mobile build.

## Proposed delivery sequence

1. **Correctness foundation:** W1 reproductions/check scope, W2 safe database ownership, W3 atomic migrations and new-event writes. Small independently reviewable change sets with regression tests.
2. **Immediate rule fixes:** W4 actor/DAO binding and existing unambiguous invariants. Keep decision-dependent semantics separate. W6 can proceed once D3 is settled; direct dependency remediation from W10 can be reviewed independently.
3. **Protocol design review, then implementation:** record D1/D4/D5 choices, approve exact state machine/wire schema/rollout, and implement W5 plus the remaining W4 rules. No finality or decentralization claim precedes the multi-node evidence.
4. **Measured performance and typed boundaries:** establish D2 baselines; approve architecture/budgets; implement W7/W8/W9 in bounded slices, with D7 settled before offline asset policy changes.
5. **Release verification:** complete W10/D6, update approved documentation through W11, and review the complete evidence for an adversarial governance release.

Protocol work can dominate the schedule under the selected D1 direction. Give estimates after the concrete bootstrap/receipt/eligibility/availability design and benchmark contract are agreed, using the already approved D8/D9 policies. This plan proposes work packages, not promises that all can ship in one release.

## Verification and release gates

For code changes, run `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, relevant Rust tests and final workspace tests, `npx vue-tsc -b --noEmit`, `npm test`, and `npm run build`. Retain the repository's command-registration, i18n, CSP, and platform-feature checks as applicable. Verify platform-specific media/FFI changes on their actual targets; a host-only pass is not mobile verification.

Add meaningful tests for migration interruption, atomic vote/tally writes, unauthorized actors, missing/revoked credentials, message ordering/replay/partitions, and overlapping lifecycle operations. Restore the relevant VC-first stress scenarios with local peers and controlled datasets; do not resurrect retired evidence topics. Use fuzz/property tests for untrusted parsers and state transitions where they find classes of failures beyond example tests.

A governance release requires the approved authority/finality model, local/remote validation parity, explicit handling of incomplete evidence, crash-safe persistence, and the reviewed D5 cleanup/activation with legacy-event rejection and a user-approved authority bootstrap. Performance acceptance requires reproducible D2 measurements. Passing builds and test counts alone do not satisfy either gate.
