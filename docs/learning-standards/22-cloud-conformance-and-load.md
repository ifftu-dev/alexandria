## Notes

2026-11-21: done. Decisions, deviations, results and open questions for the owner.

- Conformance in CI. A new job in the hosted service's CI runs `scripts/xapi-conformance.sh`: it fetches ADL's lrs-conformance-test-suite at a pinned commit (5bc232d349c60faded8240da698f195106091638), installs its packages from a lock file kept in the hosted service's repository (the suite publishes none, and unpinned packages would let an upstream release fail an unrelated change), and runs an ignored integration test that serves the record store's router on a loopback port, gives each version a fresh organisation and interface credential made through the console API, and fails on any failed test or a run that stops before every test reported. Same Postgres service and Node version as the existing jobs. Locally, end to end through the script (fresh database, clone, `npm ci`, both versions): xAPI 1.0.3 1365 of 1365 passed, xAPI 2.0 1435 of 1435 passed, under Node 22.23.4 (the CI version) and Node 26. A deliberately wrong credential turns it red. GitHub Actions itself was not run (no runner here); the workflow passes actionlint.
- The app and the store agree. The app crate `alexandria-studio` now keeps its statement builder's output as a fixture (`fixtures/xapi-store/builder-output.json`, 21 statements: every action, the SCORM and cmi5 profiles, a SCORM 2004 session through the profile mapping, pairwise, real-DID and proposed-account actors, a private course, and the identifier edges: percent-encoded and IRI package activity ids, an id of exactly 2083 characters, the activity and interaction digest fallbacks); its test fails when the builder and the file drift. The hosted service holds byte-for-byte copies of that file and of the canonical r01 to r09 statements (both versions), as with the vendored crates, and an integration test posts them in both versions as the outbox does, reads each back intact, and queries by the `urn:uuid` account actor, by each edge-case activity id, by related course and by registration, plus the activities and agents resources.
- Bug found by that test, fixed: the record store refused every statement the app sends (`account.homePage must be an absolute IRL`) and every agent query for its learners. The store now takes any absolute IRI as an account home page; a home page with no scheme is still refused, which is what the conformance suite checks. Deviation from the letter of xAPI (which says IRL), matching the reference store and the three others ticket 12 tested.
- Load test (`scripts/xapi-load.sh`, `tests/xapi_load.rs`). Records: 1,000,998 statements (1,000,000 seeded plus one voiding statement per thousand) across 20 organisations; the measured organisation holds 500,500 of them from 5,000 learners in 40 courses (one registration per learner and course, one year of `stored` times, the builder's statement shapes and DID URL ids); the other 19 share the rest in the same tables. Table with indexes 2.5 GB. Postgres 16.15 in a container with default settings (128 MB shared buffers, 4 MB work_mem), on a laptop (Apple M4 Pro), release build, each query run once to warm and then 5 times through the HTTP interface (credential, version header, formatting and access logging included). Seeding took 888 s.
- Load test results at 1,000,998 records, page size 100 unless stated (median / slowest of 5, ms): latest page 8.0 / 9.0; by agent 6.7 / 8.8; by agent with related agents 6.1 / 7.6; by a common verb (completed, about 100,000 matches) 8.2 / 9.2; by activity (element) 7.5 / 8.2; by related activity (course) 9.6 / 12.7; by registration (3 rows) 7.0 / 7.9; since a week ago 8.6 / 9.8; a 30-day window ascending 7.7 / 8.6; verb since a week ago 10.3 / 11.7; agent and verb 8.3 / 9.1; verb and related course, ids format 12.2 / 15.0; a full page of 500 9.6 / 10.3; one statement by id 5.5 / 7.3; activities resource 16.9 / 20.5; agents resource 5.5 / 7.1; five pages through `more` 10.9 / 11.7 per page. Writes through the interface after the load: 2,000 statements in batches of 100, 194 ms per batch (516 statements/s).
- Bound: every query's slowest run at most 500 ms, and no statement query's executed plan (`EXPLAIN ANALYZE`) scans the statements table sequentially; the test fails otherwise. The bound leaves room for CI runners and debug builds; the measured worst at a million rows is 20.5 ms. CI runs the same test at 200,000 statements in a debug build after the conformance suite.
- Index gaps the load test found, fixed (hosted service migration 0062). Before the fix, at 100,000 records, an agent query with related agents took 7 s, agent, verb and related-activity queries about 0.7 s, and every unfiltered page scanned the organisation's rows for the voided check. Causes: (1) requests run as the application role under row-level security, and Postgres never uses a non-leakproof condition (array containment, the `xapi_*` functions) as an index condition, so ticket 20's GIN expression indexes served no request; (2) the voided check hashed every statement of the organisation; (3) a filtered query materialised every matching id before applying time, order and limit; (4) once indexed, a related-course query still walked all statements newest first until it reached that course's last activity (1.2 s at a million rows). Now a statement's agents, related activities and StatementRef target are rows beside it, written by a trigger on every insert (both write paths), each with the statement's `stored` time, compared by equality; a page is read from one key's rows newest first and stops at its size; StatementRef matches are a second, separately limited set found from the organisation's StatementRef rows. The GIN and StatementRef expression indexes are dropped. The spec's "filterable fields are stored as indexed columns beside the statement body" now holds for every filter (columns for verb, activity, registration and time; key rows for agents and related activities).
- Known gaps and limits: shared records (statements under a learner's share, which add the share and enrolment check per row) are not in the load mix; the StatementRef part of a filtered query reads all of an organisation's StatementRef rows, which is cheap while voiding and statement references are a small share of statements; writing a statement's key rows costs about 0.7 ms per statement in Postgres (the agent-key functions from migration 0060), which a later change could move into the writer; no load test of the document resources; write throughput is recorded, not bounded; the seed drops and rebuilds the secondary indexes around the bulk load (writes measured afterwards go through every index). The hosted run for the certificate is ticket 28.
- Method: test-first at the record store seam. The agreement test was red on the home page before the validator change; the load test was red (over the bound and sequential scans) before migration 0062. The conformance wiring was checked red with a wrong credential.
