# The record store's statements resource

Triage: done
Repos: alexandria-cloud
Part of: docs/learning-standards-spec.md
Blocked by: docs/learning-standards/18-cloud-ingest.md

Spec: Record store (hosted service); user stories 55 to 57, 62 to 67.

- Each organisation has its own endpoint base and its own interface credentials with read or write scope, created and revoked in the console.
- The statements resource for xAPI 1.0.3 and 2.0: storing single and multiple statements, retrieval by identifier, query filters, paging, voiding and attachments, with the standard's version negotiation and error responses.
- Queries use the indexed filter columns. Tenant isolation is enforced in the data layer, not only at the route.
- Statements written by an organisation's own tools are that organisation's data and are not subject to a record share.
- One access-log entry per query and per learner whose records it returned, written in a single batch.

Done when: integration tests cover each operation in both versions, a credential of one organisation never reading another's records, read and write scope, and the access-log batching; the statements portion of the official conformance suite passes locally.

## Notes

2026-11-20: done. Decisions, deviations and open questions for the owner.

- Endpoint base. Each organisation's store is `<PUBLIC_URL>/xapi/<organisation id>/`; the statements resource is `statements` under it. Anything else under the base answers a JSON 404 instead of the console page. The organisation id is in the path rather than a slug or host name, since organisations have no stable slug and the service has one public URL.
- Credentials. HTTP Basic, the scheme the specification requires every store to support (the conformance suite supports nothing else). The key is the user name and a random 32-byte secret the password; only a SHA-256 of the secret is kept, in a column the application role cannot read, and it is matched on the owner pool before any tenant is set. Each credential has read scope, write scope or both. Administrators create (secret shown once), list and revoke them in the console (Operations → Record store, `/api/xapi/credentials`); creating and revoking go on the audit chain. A credential presented at another organisation's base is refused with 403; a missing, wrong or revoked one with 401.
- Statements resource. PUT and POST, single and batch (all or nothing), GET by `statementId` and `voidedStatementId`, the agent, verb, activity, registration, related_activities, related_agents, since, until, limit, ascending, format and attachments parameters, `more` links (an opaque token holding the query and where the page stopped, bounded by the first page's time so pages do not shift), voiding, multipart attachments, signed statements, the 1.0.3 alternate request syntax (refused for 2.0), version negotiation, Last-Modified and X-Experience-API-Consistent-Through. Unknown, repeated or mis-cased parameters are 400; an id already holding a different statement is 409; a re-sent identical statement changes nothing.
- Validation is the store's own (`src/xapi_store/validate.rs`): closed property sets, one identifier per agent, IRIs, language tags, ISO 8601 timestamps and durations, groups, sub-statements, interaction components, attachments, context agents and groups for 2.0, and the version property (1.0.x always, 2.0.x from 2.0 clients). An error names the property to correct.
- Signed statements. Only RS256, RS384 and RS512 (ticket 12). The payload must match the statement, durations compared to the hundredth of a second. When the header carries `x5c`, the signature must verify with the first certificate's key; without it there is nothing to verify against and the statement is accepted on structure, as the specification allows. Certificate chains are not checked against any trust root.
- What the store adds. `stored` (milliseconds, UTC), `timestamp` when absent, `authority` (always overwritten with the credential as an account agent under the endpoint base), and `version` when absent (1.0.0 for 1.0.3 clients, 2.0.0 for 2.0 clients). Context activities always come back as lists. Shared records keep their body as received; on the way out their authority is the learner's own actor, since the learner's app signed the batch they came in.
- Queries. The filter fields are the indexed columns from ticket 18 plus indexed expressions over the body (migration 0064: agents, related agents, related activities, StatementRef targets, voiding targets), so every row is covered whichever path stored it, with no change to ingest. Statements that target a matching statement match too, recursively, as the specification requires; that is a recursive query over the target index. Its cost at size is for the load test in ticket 22.
- Tenancy. Every read and write goes through `xapi_store::records::Records`, which holds a tenant transaction for the credential's organisation; row-level security filters every query and every query also names the organisation. The new tables (credentials, attachments, attachment links) have row-level security like the rest. Statement ids are per store: two organisations can hold the same id.
- Shared records. Returned beside the organisation's own statements only while the share is active and the learner's enrolment lasts (read-time filter, using ticket 18's enrolment rule). The organisation's own statements are not subject to any share or enrolment. An id removed earlier (revoke, enrolment end, retention) cannot be stored again through this interface either (409), so a removed record cannot be written back under its old id.
- Access log (deviation from a separate log). Reads are written to the learner's existing access log (`cohort_access_log`), which the learner already reads with a signed request: one named entry per read and per learner whose shared records it returned, in one insert. A credential is not a staff member, so the log's role became optional, with `credential_id` and `via_record_store` naming the reader (constraint: one or the other). The learner sees these entries with the role `record_store`. Statements an organisation's own tools wrote name no Alexandria learner and log nothing.
- Retention. The organisation's own statements follow the same 180-day constant as shared records (ticket 18). Attachment content is deleted by the retention sweep once no stored statement names it.
- Limits. Request bodies up to 16 MiB; a page holds at most 500 statements (also what `limit=0` means).
- Conformance suite (ADL lrs-conformance-test-suite, fetched from GitHub and run with Node against a local server and Postgres). Statements portion: everything passes for 1.0.3 (1218 passed, 144 failed, all in the document, agents, activities and about resources) and for 2.0 (1249 passed, 180 failed: 179 in those resources plus "When storing or comparing IRIs ...", which reads the activity back through the activities resource). Those are ticket 21's. Wiring the suite into CI is ticket 22: it needs the suite fetched (`git clone --depth 1 https://github.com/adlnet/lrs-conformance-test-suite`, `npm install`), an organisation and credential inserted (no console session needed), and `node bin/console_runner.js -e <PUBLIC_URL>/xapi/<org> -a -u <key> -p <secret> -x 1.0.3|2.0.0`; the JSON report lands in the suite's `logs/`.
- Not done here (follow-ups): the about, agents, activities and document resources (ticket 21); CORS for browser-based xAPI clients; `/xapi/` is not rate limited (the limiter only meters `/api` and `/auth`, and a 32-byte secret is not guessable, but a credential can make unlimited requests); statements written through this interface are not forwarded to an organisation's external store (ticket 19 forwards shared records only); a learner-facing count of record-store reads in the app's grant view; the app's access-log screen may show the new `record_store` role verbatim.
- Test fixtures: the RSA key used to sign test statements is the conformance suite's public test key; the certificate is self-signed for it. Both are committed under `tests/fixtures/xapi/` (force-added past the `*.pem` ignore, like the existing FCM test key).
- Method: tests were written beside each slice at the record store seam the spec names (HTTP against Postgres), not strictly test-first for every slice; the retention slice was red before green.
- Proposed doc edits, not made: the hosted service's `docs/organisations.md` should gain a "Record store" section (endpoint base, credentials and scopes, what is logged and where, retention, the 16 MiB limit) and the two console routes in its access table; `docs/deployment.md` should note that a proxy in front must pass `/xapi/` with request bodies up to 16 MiB and the `Authorization` header; its `AGENTS.md` route-auth note could mention `credential_of(` beside the other authorisation calls; the spec's Record store section could say the learner's access log is where record-store reads are disclosed.

### Review (2026-11-21)

- `/xapi/` is rate limited (its own classes in `ratelimit`): keyed by the credential a request presents (the Basic user name, unverified, so the limiter itself does no database read), by address when it presents none, with a wide budget (6,000 a minute, burst 3,000) that a conformance run fits in. Sign-in failures are also counted per address (30 a minute) and checked before the credential is looked up, so rotating made-up keys does not buy more guesses.
- Residency: `credentials::authenticate` reads the organisation's residency and refuses, with 403, a deployment in another region, as the console's `org_of` does.
- `xapi_statements.actor_key` is dropped and the statements resource no longer writes it (ticket 18); `query::agent_key` is the one agent normaliser. The expression indexes 0064 created and 0066 dropped are no longer created (migrations edited, pre-launch).
- The served versions are listed once (`XapiVersion::ALL`, `served()`): the about resource, the console's credentials page and the forwarding settings all derive from it.
