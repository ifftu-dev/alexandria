# Hosted ingest of shared records

Triage: done
Repos: alexandria-cloud
Part of: docs/learning-standards-spec.md
Blocked by: docs/learning-standards/17-record-share-grant.md

Spec: Record store (hosted service) → ingest, named access, retention; Sending records → revoke.

- An ingest endpoint accepts signed batches, checks each statement against the share's scope and stores it. The filterable fields are stored as indexed columns beside the statement body from the start.
- Revoking deletes the records received under that share and keeps only their identifiers so they cannot be re-inserted.
- Records stay readable by name only while the share is active and the learner's enrolment with the organisation lasts. After either ends they are deleted or, where retention keeps aggregates, reduced to counts that obey the existing minimum cell size.
- Records follow the organisation's retention policy. Tenant isolation is enforced in the data layer.
- An administrator can see which learners have an active record share and when each last synced.

Done when: integration tests against Postgres cover scope enforcement at ingest, a batch with a bad signature refused, deletion on revoke with re-insertion blocked, the end-of-enrolment rule, tenant isolation and the share status listing.

## Notes

2026-11-20: done. Decisions, deviations and open questions for the owner.

- Ingest. `POST /api/grants/{id}/records` takes the app's signed batch unchanged. It checks the signature by the grant's subject, then the grant (same grant and subject, not revoked, shares records, every actor is the grant's account), then every statement: its activity must sit under a course in the scope (activity ids are DID URLs `<creator>/courses/<id>/...`), and an interaction-level statement (verb `responded`, an interaction definition, or an interaction path) needs the interaction kind. One statement outside the scope refuses the whole batch with 400, so the app retries one by one and only the stray statement fails visibly. A bad signature is 401; a revoked share, or a learner whose enrolment ended, is 409. The response counts `stored`, `duplicates` and `withheld`.
- Storage. One table, `xapi_statements`, with the query filter fields as indexed columns (actor, verb, activity, registration, timestamp, stored) beside the body, plus the share's grant, subject, course and kind. Statements an organisation's own tools write later (ticket 20) can go in the same table with no grant.
- Retries and replay. Statement ids are stable per recipient, so a statement already held counts as a duplicate and is not stored twice. Replay protection comes from the data, not from the batch id; the batch id is not recorded. A statement re-sent with the same id and different content is also a duplicate (the first copy stays).
- Revoke. Deletes the share's records in the transaction that records the revoke and keeps only their ids. A deleted id is never stored again, under any share, and is counted as `withheld` rather than refused, so the app does not retry it forever. Records deleted because enrolment ended or retention expired get the same treatment.
- Enrolment (interpretation). "The learner's enrolment with the organisation lasts" is read as: the organisation enrolled them and at least one enrolment row is still open. A learner the organisation never enrolled is governed by the share alone; otherwise an organisation that does not use cohorts could never hold shared records. Owner to confirm. Under the strict reading the rule is one SQL constant to change (`shared_records::ENROLMENT_ENDED`).
- End of enrolment. When the last enrolment ends, the learner's shared records are reduced to counts per course and verb (learners and statements) and then deleted. This runs straight away when the enrolment endpoint ends it, and in the retention sweep for an enrolment ended any other way. The counts are reported only through the cohort minimum cell size, and the statement count is withheld with a withheld learner count. The cohort precedent ("historical cohorts stay reportable in aggregate") is taken as the retention policy keeping aggregates. A revoke deletes without keeping counts, since the spec says revoke deletes.
- Retention. No per-organisation retention policy exists. Records follow the one the console already states: 180 days, now a single constant `retention::RETENTION_DAYS` that assessment runs and shared records both use (the literals in the run routes and the settings response now use it; the demo seeder keeps its own). Records past it are deleted by the retention sweep.
- Narrowing (open question). A narrowing grant update drops the app's unsent records outside the new scope, but this service keeps the records it already received from courses that were narrowed away. The spec only says revoke deletes. The snapshot precedent (a narrowing deletes a snapshot that no longer fits) argues for deleting them too. Owner to decide.
- Share status. `GET /api/record-shares` (administrators only, because it names people) lists active shares: subject, scope, when granted, last sync (`access_grants.records_synced_at`, set on every accepted batch), records held, and enrolment `current`, `ended` or `none`, plus the counts left by ended enrolments. The console shows it on the Access page to administrators.
- Not done here: forwarding to an organisation's own store and voiding on revoke (ticket 19), and reading records through the xAPI statements resource (ticket 20). Ticket 20 must filter named reads by the active share and enrolment (see the handoff note); the ingest-time and sweep-time rules leave nothing for it to filter, but a read-time filter is still needed between an enrolment ending by a path that does not reduce the records and the next sweep (up to six hours).
- Proposed doc edits, not made: the hosted service's `docs/organisations.md` access table should add `POST /api/grants/{id}/records` (learner, signed batch) and `GET /api/record-shares` (administrator), with a short "Record shares" section covering scope checks, deletion on revoke with tombstones, the end-of-enrolment rule and retention; the retention section of its `src/retention.rs` module docs already lists shared records. The spec's Record store section could state the enrolment interpretation and that counts kept at enrolment end are per course and verb.

### Review (2026-11-21)

- **Narrowing now forgets (reverses the earlier reading above).** Withdrawing consent for a course or for responses must stop named access to what was already received under it. An update that narrows a share deletes, in the transaction that records it, the records outside the scope it keeps and tombstones them (new reason `narrowed`); forwarded copies are voided at the organisation's store (ticket 19). An update that keeps the skills but drops the record scope ends the share for records exactly as a revoke does (tombstone reason `revoked`), and new batches under it answer 409. Owner may override.
- Scope check tightened. A response in the result, or an interaction among the context activities, makes a statement interaction-level; every course a statement's context activities name (parent, grouping, category, other; a list or a lone activity) must be in the scope. Activities under no course (categories, profiles) are allowed. A sub-statement object was already refused.
- The share listing pages: `GET /api/record-shares?after=<cursor>&limit=<n>` returns newest grant first, at most 100 a page by default (200 at most), with `next` (null on the last page). It used to stop silently at 500 and order by last sync; the console's Access page shows more on request.
- One agent key. `xapi_statements.actor_key` (written and indexed, never read) is gone, with `shared_records::actor_key`, whose account-first format disagreed with the agent filter. `xapi_store::query::agent_key` mirrors the database's `xapi_agent_key` and a test holds them together. Pre-launch and undeployed, so migration 0062 was edited rather than followed by a drop.
- The enrolment rule is `shared_records::enrolment_ended_sql(org, subject)` (column names or parameters) instead of a string with placeholders replaced; the interpretation question above is now about that function.
